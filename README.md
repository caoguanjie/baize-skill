<h1 align="center">白泽.skill</h1>

![白泽：先看图，再读码。让业务有脉络，让代码有坐标。](assets/banner.png)

**给旧项目一张能查代码、能跟着改动更新的业务地图。**

不用先搞清楚入口在哪。告诉 AI：“登录后为什么又回到登录页？”白泽会从代码里找线索，与你确认入口和范围，再把真实流程、异常分支和实现位置画出来。

**安装到项目里，不装到全局。** 下载本仓库 ZIP，解压后把目录改名为 `baize-skill`，放到项目的 Skill 目录。Claude Code 用 `.claude/skills/baize-skill/`，Codex 用 `.agents/skills/baize-skill/`；[其他客户端与多客户端共用方式](#安装与升级)见下文。

在 Claude Code 中试一句：

```text
/baize-skill 登录后偶尔又被踢回登录页，帮我理一下
```

[看账号登录样例](examples/账号登录.md) · [快速开始](#快速开始) · [可选源码图谱 MCP](#推荐搭配源码图谱-mcp) · [AI 操作说明](SKILL.md)

## 一张图理解白泽

```text
业务全景              这项业务从哪里开始，最后到哪里？
    |
    v
模块总览              当前阶段接收什么，又交给下一步什么？
    |
    v
子模块详图
    +-- 左边：业务流程与分支 -- 用户做什么，成功和失败去哪
    |
    +-- 右边：实现分层与入口 -- 哪段代码负责，从哪里继续查
                |
                v
            源码锚点表    文件 + 行号 + 方法/接口/数据标识
```

简单业务可以跳过模块这一层。人和 AI 读的是同一份 Markdown，不维护两套容易对不上的图和数据。

## 为什么做这个

接手旧项目，最费时间的往往不是读懂一个函数，而是拼出一件事：

“这个按钮点下去，经过哪些校验？谁改了状态？哪个后台任务接着做？失败了回到哪里？”

实现按目录分散，业务却是连着发生的。单看一个文件，很难知道它在整条路上负责哪一段：

- 产品想确认规则有没有落地，却要跨很多文件找答案。
- 测试能找到正常路径，容易漏掉取消、过期、重试和后台接力。
- 开发改一个状态前，要反复查谁写、谁读、哪些地方受影响。
- AI 每次从全项目搜起，读进一堆同名但无关的实现，下一次还要再找。

白泽不替换代码分析工具。它把“业务语言”和“代码位置”接起来：先知道自己在哪条路上，再进代码核对。

## 把它想成地图

| 地图里的东西 | 白泽里的对应 |
| --- | --- |
| 全国地图 | 业务全景：先看完整走向 |
| 城市地图 | 模块总览：看当前阶段 |
| 街区详图 | 子模块左右双栏图：看每个分支 |
| 门牌号 | 节点号，例如 `N1.01`，通向源码锚点 |
| 修路通告影响哪些路段 | `refs --git`：未提交改动涉及哪些已记录链路 |
| 地图过期检查 | `check`：查失效入口、结构问题和新鲜度线索 |
| 老司机的笔记 | 探查经验：记下怎么找路，不记死答案 |

地图不能证明一辆车实际走过哪里。同样，链路图不能证明某次请求走过哪些分支；排查真实故障仍要结合日志、状态或测试复现。

## 五条原则

| # | 原则 | 意味着什么 |
| --- | --- | --- |
| 1 | 当前代码说了算 | 旧文档、需求和经验提供线索，不能代替本次核对 |
| 2 | 有什么就画什么 | 纯前端、纯后端、脚本都能画，不强求全栈 |
| 3 | 不确定的写进「未核对」 | 不把猜测补成一条看似完整的箭头 |
| 4 | 关键处停下来问人 | 首次项目设置、每次入口、每次范围都要确认 |
| 5 | 经验由证据决定状态 | 独立案例支持才升级，遇到反证就降级 |

## 左边讲业务，右边找实现

```text
左边：业务流程                     右边：实现落点

提交订单 [N1.01]       <------>    [N1.01] 页面层
    |                             方法：submitOrder()
    v                             动作：读取输入、发起请求
检查输入
    +------------------+
    |                  |
    v                  v
资料完整             缺项提示
    |
    v
创建订单 [N1.02]       <------>    [N1.02] 服务层
                                  方法：OrderService.create()
                                  表：orders  写
```

上面是阅读示意。实际详图用一张带外框的双栏图，左右通过节点号对应；不为对齐卡片把左边流程拉得很长。完整文件路径、行号和精确符号放在图下的源码表。

- 产品经理沿左边读：入口、判断、结果是否与需求一致。
- 测试人员沿分支读：失败停在哪，什么条件可以重试。
- 开发人员和 AI 按节点进入右边，再打开对应源码。

“层名”不绑定某套架构。前端项目可以是页面层、组件层、状态层、请求层；后端项目可以是路由层、服务层、数据层。首次使用时 AI 根据实际目录起草，你确认后保存在 Skill 里。

## AI 查代码，前后有什么不同

```text
没有地图
业务问题 -> 全项目搜关键词 -> 打开很多候选 -> 猜入口 -> 反复补查上下游

有地图
业务问题 -> 业务 -> 模块 -> 子模块 -> 节点 -> 打开相关源码核对

知道文件或方法
文件/方法 -> refs -> 命中的链路和节点 -> 核对当前实现
```

它减少的是无关阅读，不是省掉核对。

Token 可以粗略理解为 AI 需要读入和处理的文字单位。有地图时，通常先读命中的子模块，不必把整项业务、整个目录都塞进上下文；已记录的交接也不用每次重新猜。

**不承诺固定节省比例。** 收益取决于项目大小、覆盖度和文档新鲜度。缺失或过期的地图，反而会增加判断成本。

## 推荐搭配：源码图谱 MCP

想让 AI 少翻无关文件，推荐选装 [codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp)。MCP 可以理解为给 AI 接工具的接口；这个工具帮 AI 查“定义在哪、谁调用了它、它又调用谁”，白泽再把查到的实现组织成业务地图。

```text
白泽确定业务入口与范围
        |
        v
源码图谱找定义、追调用 -> 只读需要的源码
        |
        v
白泽画出流程与锚点 -> 用 refs 反查、用 check 检查文档
```

两者分工不同：白泽的 `refs` 查**已经写进链路文档的引用**，MCP 查**源码之间的关系**。配合使用有助于减少盲搜和无关上下文，后续探查也可能更快；首次建立索引有成本，效果取决于项目规模、语言支持和索引覆盖，不保证固定的提速或 Token 节省比例。

**可选，不是前置依赖。** 没有它，白泽照常用文本搜索。已经有合适的源码检索工具，也不必换掉。

### 不会安装？把这段话发给 AI

在能读写当前项目、执行终端命令的 AI 编码客户端中，复制下面这段：

```text
请帮我安装 codebase-memory-mcp，并接入当前项目使用的白泽 baize-skill。
官方仓库：https://github.com/DeusData/codebase-memory-mcp

先读取官方最新安装说明，识别我的系统、AI 客户端和现有 MCP 配置。
如果已经装好就复用，不要重复安装。
先说明将下载或执行什么、修改哪些配置、索引哪个目录，等我确认后再操作。
优先使用当前项目级配置；如果客户端只支持用户级配置，先说明影响，不要悄悄改。
保留已有 MCP 配置和项目规则，不要直接覆盖 AGENTS.md 等指令文件。

接入后确认当前会话能调用工具，复用或建立已确认范围的索引，
再用项目里的一个已知符号确认能找到正确源码。
成功后更新白泽 Skill 内 references/项目设置.md 的「代码图谱工具」、
「图谱项目」和「图谱范围」，让白泽优先用图谱查关系、覆盖不足时读源码补查。
如果项目设置还不存在，先起草完整设置给我确认。
不要改业务代码、其他设置或探查经验，不要提交或推送。
需要我批准权限、重连或重启客户端时请告诉我，不要提前宣称完成。
```

AI 可以按这段要求代办安装和接入，但客户端权限、系统授权和重启步骤可能仍需要你操作。**安装成功、会话连通、项目已索引，是三件不同的事**；不能只看到安装命令成功就开始依赖图谱。

官方默认安装方式可能修改用户级配置：Claude Code 的手动配置支持项目级 `.mcp.json`，Codex 使用自己的配置方式，不能直接照搬。让 AI 读取[官方手动配置说明](https://github.com/DeusData/codebase-memory-mcp#manual-mcp-configuration)，而不是不看影响就执行默认安装器。

### 装好以后，白泽怎样用上它

公开版已内置[源码图谱追查规则](references/源码图谱MCP.md)，不需要每个使用者再手改一遍 `SKILL.md`。AI 接入成功后，只需按你的授权更新 **Skill 内的项目设置**：

```text
代码图谱工具 -> 选用 codebase-memory-mcp，明确补查方式
图谱项目     -> 核实后的索引标识，不猜项目名
图谱范围     -> 索引根与当前目录的关系，以及本次允许检索的范围
```

下一次调用白泽，它先读设置，再检查当前会话的工具和索引是否可用。能用就优先查定义和调用关系；缺失、过期或覆盖不全时，说明缺口并回到源码搜索，不把“没有搜索结果”解释成“没有实现”。已有准确锚点时直接读对应源码，不为使用 MCP 重复搜索。

若已安装，可以直接说：“请确认当前项目的 codebase-memory-mcp 连接和索引，把白泽的项目设置接上它，其他设置与规则保持不变。”

官方说明索引在本地处理，但检索结果仍会进入你使用的 AI 客户端和模型上下文；源码权限与数据政策照常适用。该 MCP 自身有本地后台服务和监听机制，和白泽的纯文件、脚本运行方式不同，详见[官方配置说明](https://github.com/DeusData/codebase-memory-mcp/blob/main/docs/CONFIGURATION.md)。

## 它能帮团队做什么

| 工作 | 白泽提供什么 | 仍需要什么 |
| --- | --- | --- |
| 读懂旧业务 | 从触发到结果的一条连续路线 | 对照有效需求，区分预期与现状 |
| 定位实现 | 节点对应文件、符号、数据或事件 | 读取当前源码，确认入口没有失效 |
| 排查故障 | 先找哪一步偏离，再查上游原因与下游影响 | 实际日志、状态记录或复现 |
| 设计测试 | 成功、失败、取消、重试、异步交接的分支清单 | 业务判断和运行验收 |
| 判断改动影响 | 从文件反查已记录的业务、节点和共用能力 | 补查未覆盖的新入口，不把命中结果当完整回归清单 |
| 评审与交接 | 产品、测试、开发围绕同一个节点讨论 | 人对业务含义与未知部分的复核 |

## 工作流程

### 第一次：先认识项目，再找这条业务

```text
你描述现象或业务
        |
        v
AI 只读勘察项目 -> 起草项目设置 -> 你确认（停顿 1，仅首次）
        |
        v
读经验索引 -> 搜入口 -> 列候选和依据 -> 你确认（停顿 2）
        |
        v
起点、终点、分支、分层、切分方案 -> 你确认（停顿 3）
        |
        v
追源码 -> 画图 -> 静态检查 -> 说明未核对项 -> 探查收尾
```

只有一个候选入口也会停下来确认。同一轮已经确认的不重复问。以后每次先读项目设置，不重新勘察一遍；需要改设置时先向你提议，不悄悄改。

### 平时：查图、改动、同步

```text
改代码前：文件或方法 -> refs -> 候选影响范围
改代码后：refs --git -> 重读命中源码 -> 更新链路 -> check --fix -> check
```

查询默认只读。生成或维护文档不等于授权修改业务代码，也不等于授权提交或推送。

### 工具分工

下列命令在**你要画图的项目目录**运行。`<skill>` 替换为实际安装路径；如果从大仓库中的子项目启动，可用 Skill 的绝对路径。

```text
node "<skill>/scripts/chain.mjs" refs OrderService.create
node "<skill>/scripts/chain.mjs" refs backend/services/orders.py
node "<skill>/scripts/chain.mjs" refs --git
node "<skill>/scripts/chain.mjs" check
node "<skill>/scripts/chain.mjs" check --fix docs/链路全景/业务/订单.md
```

| 工具 | 做什么 | 不做什么 |
| --- | --- | --- |
| `refs` | 按文件、目录、符号、表名、接口等查文档锚点 | 不自动遍历所有代码，不证明无命中就无调用 |
| `refs --git` | 反查当前目录内未提交改动，包括删除和未跟踪文件 | 不包含目录外改动，不是完整的跨服务影响分析 |
| `check` | 核对结构、版式、链接、锚点；按条件查接口、新鲜度 | 不证明业务正确、功能跑通或线上配置生效 |
| `check --fix` | 修可唯一定位的漂移行号，重建有标记的顶层交叉表 | 不修改业务流程、源码、节点号和图形布局 |

`check` 退出码：0 表示没有错误（仍可能有提示），1 表示文档错误，2 表示参数或前置条件不满足。没有项目设置时先走首次使用；没有接口契约时跳过接口核对并提示；非 Git 目录仍可做普通查询和静态检查，但没有新鲜度检查，`refs --git` 不可用。

## 两种持续维护，不是一回事

**链路同步**让地图跟上代码：改动后重读实现，更新流程与锚点。

**经验积累**让下一次找路少绕弯：这次沿注册表追到了真实消费者，就留下适用条件、关键误路和证据，下次只加载相关经验。

```text
一次真实探查
    |
    v
单次观察 -- 独立案例再次印证 --> 已稳定复现
    |                             |
    +---------- 新反证 -----------+
                    |
                    v
                  待复核 -- 已确认不再适用 --> 失效
                    |
                    +-- 重新划定条件、补证后再判断状态
```

| 状态 | 怎么用 |
| --- | --- |
| 单次观察 | 先验证当前场景，再用这个追法 |
| 已稳定复现 | 条件匹配时优先用，仍核对当前连接 |
| 待复核 | 暂停依赖旧结论，重查受影响的范围 |
| 失效 | 留下历史与原因，避免重踩 |

同一个案例重跑十次，不是十个独立案例。经验有反证就修，不为了让“经验库越来越大”保留错误结论。

经验留在 Skill 的 `references/探查经验/`；索引只放卡点、摘要、状态和详情入口，AI 按需读详情。发布包不预填“实战经验”，只有真实任务得到可回查证据、且允许维护时才创建。

这不是模型训练，也不是无人值守的后台学习。白泽自身不提供常驻服务；选装的源码图谱 MCP 有独立的后台机制。经验积累只是 AI 按规则读文件、核验证据、把可复用的方法写回项目文件。没有新收获就不写；明确只读时只报告候选。细则见[经验维护规范](references/经验维护规范.md)。

## 白泽不会做的事

1. 搜索没有结果，就断定“没有调用”。
2. 用旧经验代替本次源码核对。
3. 把静态检查通过说成运行验收通过。
4. 只找到一个入口，就直接开始画。
5. 自己悄悄修改项目设置。
6. 把同一案例重跑当成独立印证。
7. 自动提交或推送。
8. 把凭据、个人资料或完整日志写进经验。

## 快速开始

你不需要先知道业务的正式名字、接口或函数。给一个现象、一段文案、一个地址，都能作为线索。

下面是 **Claude Code / Copilot / Cursor** 的写法：

```text
/baize-skill 用户登录是怎么走的
/baize-skill 登录后偶尔又被踢回登录页，帮我理一下
/baize-skill 从「立即支付」按钮开始画
/baize-skill 订单超时没有自动取消，这块怎么跑的
/baize-skill 先帮我看看这个项目有哪些主要业务
```

Codex 把开头换成 `$baize-skill`。Gemini CLI、OpenCode 可明确说“请使用 baize-skill 为这个项目生成登录的业务链路全景”，由客户端激活 Skill；不要把斜杠命令当成所有客户端通用语法。

### 首次对话会像这样

```text
你：登录后偶尔又被踢回登录页，帮我理一下。

AI：这是纯前端项目。我找到了页面路由、登录状态和响应拦截器，
    没有后端源码或接口契约。建议用页面层、状态层、请求层。
    这是项目设置草案，确认后保存到 Skill 目录。

你：确认。

AI：找到两个入口：登录按钮；接口返回 401 后清理会话。
    各自的文件和处理函数是……你要从哪个入口开始？

你：从登录按钮开始，把 401 回退也包括进去。

AI：范围：按钮 -> 校验 -> 请求 -> 响应 -> 保存状态/失败提示，
    包含后续 401 导致回退。后端内部不在当前项目，标外部。
    分成登录与会话回退两段，可以吗？

你：可以。

AI：按范围追代码、写文档并检查；不能确认的地方单独列出。
```

这是交互示意，不是实际验证记录。AI 找不到候选时，会先列主要业务让你选，而不是猜一条链路。

### 使用前留意

- 使用具备项目文件读取能力、并支持 Agent Skills 的客户端。
- 工具脚本需要 **Node.js 22+（推荐已验证的 22 LTS）**，使用 `.mjs` 和 Node.js 内置模块，**不需要 Python，也不需要 `npm install`**。Git 只用于改动反查与新鲜度检查；没有 Git 仍可做普通反查和静态检查。
- 首次先做一条链路，不必一次画完整个项目。你仍需审阅业务含义。
- AI 读取的代码受你所用客户端和模型服务的数据处理政策约束；确认项目允许这样使用，不把敏感信息写入设置和经验。
- 输出在**当前目录**的 `docs/链路全景/`，不是强制写到 Git 顶层。请始终从同一项目目录调用；不同子项目不要共用一份项目设置。

## 安装与升级

### 选项目级目录

以下按官方文档核对，客户端版本变化时以对应链接为准：

| 客户端 | 推荐安装位置 | 调用 |
| --- | --- | --- |
| [Claude Code](https://code.claude.com/docs/en/skills) | `.claude/skills/baize-skill/` | `/baize-skill` |
| [Codex CLI](https://learn.chatgpt.com/docs/build-skills) | `.agents/skills/baize-skill/` | `$baize-skill` 或从 `/skills` 选择 |
| [Gemini CLI](https://geminicli.com/docs/cli/skills/) | `.gemini/skills/baize-skill/`，也支持 `.agents/skills/` | 提示中明确要求使用，由模型激活 |
| [Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills) / [VS Code](https://code.visualstudio.com/docs/copilot/customization/agent-skills) | `.github/skills/baize-skill/`，也支持 `.claude/skills/`、`.agents/skills/` | `/baize-skill` |
| [Cursor](https://cursor.com/docs/context/skills) | `.cursor/skills/baize-skill/`，也支持 `.agents/skills/`、`.claude/skills/` | `/baize-skill` |
| [OpenCode](https://opencode.ai/docs/skills/) | `.opencode/skills/baize-skill/`，也支持 `.agents/skills/`、`.claude/skills/` | 提示中明确要求使用，由模型调用 |

不采用全局安装：项目设置和经验属于当前项目，不该串到另一个项目里。

### 方式一：下载 ZIP

1. 在本仓库点击 **Code → Download ZIP**。
2. 解压，把 `baize-skill-main`（或带其他分支后缀的目录）改名为 `baize-skill`。
3. 放进上表对应目录，确认 `SKILL.md` 直接在 `baize-skill/` 下，不要多套一层文件夹。
4. 重新打开客户端会话，确认能发现白泽，再描述你想看的业务。

### 方式二：Git 克隆

从本仓库 **Code** 按钮复制克隆地址。以下以 Claude Code、首次安装且目标不存在为例；把第一行的文字替换为复制的 URL：

```bash
REPO_URL='替换为本仓库的克隆地址'
mkdir -p .claude/skills
git clone "$REPO_URL" .claude/skills/baize-skill
```

完成后，删除**新克隆的 `.claude/skills/baize-skill/.git`**，让 Skill 普通文件随你的项目管理，避免形成嵌套仓库。不要删除你项目根目录的 `.git`。仓库地址由发布后的本仓库提供，不使用猜测的账号地址。

### 多个客户端共用一份

不要复制多份白泽，否则每份会各自积累设置和经验。推荐把真实目录放在 `.agents/skills/baize-skill/`，为 Claude Code 建链接（macOS/Linux，目标不存在时）：

```bash
mkdir -p .claude/skills
ln -s ../../.agents/skills/baize-skill .claude/skills/baize-skill
```

Claude Code、Codex 官方明确支持技能目录符号链接；Gemini CLI 也提供基于链接的 `skills link`。其他客户端的相应文档没有明确承诺符号链接支持，使用时自行验证，不把“能扫描同一真实目录”和“支持符号链接”混为一谈。

Windows 可直接把唯一真实目录放到客户端支持的位置；需要链接时，按系统权限和客户端实际支持配置。不同项目各装一份，不跨项目链接同一个带设置的目录。

### 升级：换工具，留项目记忆

先备份，再用新版本替换发布包文件，**保留**：

```text
references/项目设置.md
references/探查经验/
```

不要整目录删了再解压。项目的 `docs/链路全景/` 也不参与覆盖。

如果你的 `.gitignore` 忽略了 Skill 目录，项目设置和经验不会随代码提交，团队其他人也就看不到。按团队要求决定哪些项目文件进入版本控制，不要把敏感资料强行加入 Git。

## 目录里为什么有 scripts 和 tests

```text
baize-skill/
├── SKILL.md                 AI 的操作说明
├── README.md / README_EN.md 人读说明
├── assets/                  README 横幅与插画
├── references/
│   ├── 版式规范.md
│   ├── 已知断点.md           13 类基础追法
│   ├── 源码图谱MCP.md        可选工具的接入与追查规则
│   ├── 项目设置说明.md
│   ├── 经验维护规范.md
│   ├── 项目设置.md           首次确认后生成，发布包没有
│   └── 探查经验/            真实探查后生成，发布包没有
├── scripts/                 .mjs：检查、反查、修行号和排版
├── tests/                   维护者验证工具和行为规则
└── examples/账号登录.md      没有配套源码的中性格式样例
```

`SKILL.md` 告诉 AI 怎么追业务，Node.js 脚本处理机械检查，`tests/` 则检查这些脚本有没有被改坏。三者职责不同。

**日常使用不需要安装 npm 包，也不需要先跑测试。** 维护这个 Skill 时，在 Skill 目录运行：

```text
node tests/run.mjs
```

脚本和这套测试只使用 Node.js 内置模块。测试用临时样本项目，不依赖你的业务代码；[行为演练](tests/experience_scenarios.md)另检验 AI 是否按规则停顿、读经验和维护边界，不能用关键词匹配代替。

Python 旧实现和对应测试已移除，工具与测试统一使用 Node.js。维护方式及迁移验证记录见 [测试说明](tests/README.md)。

字宽分类固定为 Python 3.13 原版使用的 Unicode 15.1.0，仍按 W/F 字符 1.62 格、其余字符 1 格计算。Python 不同版本原本就可能采用不同 Unicode 数据；固定数据后，Node.js 升级不会自行改变排版。

## 适用范围与边界

适合接手旧项目、调用跨多层、异步交接多、关键词常搜出同名实现，以及产品、测试、开发需要共同理解业务的情况。只有几个短流程的小项目，维护完整地图的收益可能有限。

| 项目 | 画什么 | 边界 |
| --- | --- | --- |
| 纯前端 | 点击、校验、请求、成功与失败后的界面变化 | 后端标外部，不猜内部 |
| 纯后端 | 请求或任务、判断、写库、消息、返回 | 不补不存在的 UI |
| 前后端都有 | 操作到业务结果 | 只包含当前项目和已确认范围 |
| 原生端 | 系统回调、桥接、插件交接 | 真机表现另验 |
| 定时任务、脚本 | 触发、逐项处理、重试、结果汇总 | 不凭代码认定线上调度已启用 |

还需要知道：

- 首次画图有成本，后续收益主要来自增量维护和按子模块阅读。
- `check` 不是业务测试、安全审计或完整静态分析器。方法定位使用正则，有歧义不会盲修；源码路径暂不支持空格。
- 接口核对当前支持 OpenAPI JSON，不支持直接解析 YAML、远程契约或自动下载契约。
- 新鲜度基于 Git 文档提交和源码变化，只是线索，不是“此文档一定正确/错误”的裁决。
- 中文字宽按 **1.62 格**、ASCII 按 1 格生成，以 Typora 校准为基础；不同查看器的字体可能有显示差异。details 内 Markdown 表格的折叠也依赖查看器支持。
- AI 是否遵守规则受模型和客户端影响。测试和演练只能覆盖已验证场景，不承诺所有模型都严格执行。
