# 版式规范

链路文档只维护 Markdown 一份真源，ASCII 图直接写在正文的 `text` 围栏里；不另存 SVG、Mermaid 或机器专用副本。业务事实以当前代码为准，本文中的路径、行号和业务都是格式示意。

## 1. 分类与切分

### 业务与能力

| 类别 | 判定 | 命名 | 例子 |
| --- | --- | --- | --- |
| 业务 | 有明确触发和可辨认结果，可以由人、请求、事件或时钟发起 | 先用项目需求的叫法，没有就按代码职责取中文名 | 账号登录、订单支付、账单归档 |
| 能力 | 没有独立业务目标，被两条以上业务共用的技术机制 | 写它做什么 | 消息可靠投递、文件上传 |

只被一条业务用到的机制直接画进该业务。能力文档讲共用机制，业务特有的事件名、状态值、消费者仍放业务文档。

文件和目录用业务名，不带日期和版本。没有前端、后端或原生端就不画那一层；外部服务不在当前目录时，画到本项目的调用和响应处理，写明外部边界，不推测服务内部。

### 三层阅读

```text
业务全景       从触发到结果，保留关键分支、模块之间交接
    |
    v
模块总览       当前阶段的连续流程、子模块清单
    |
    v
子模块详图     左栏业务流程 + 右栏实现卡片 + 源码锚点表
```

先按业务阶段切模块，再按触发方式或共同后半段切子模块，不能按技术目录切出“前端子模块”“数据库子模块”。技术层写在右栏卡片上。

| 变化 | 处理 |
| --- | --- |
| 换参与角色，或隔着一次明确异步交接 | 切模块，例如下单、发货 |
| 换触发方式，或者存在平行的登录方式 | 各一个子模块 |
| 多条路共用后半段 | 汇入一个子模块，不重复画 |
| 一张详图超过 12 个节点 | 按实际交接继续拆子模块 |

- 单文件：只有一个阶段、没有独立的后台异步阶段、子模块不超过 6 个，直接列子模块。例如账号登录。
- 目录：多个角色或异步阶段，或者子模块超过 6 个；目录中放 `总览.md` 和模块文件。
- 一份文件最多 6 个子模块，一个业务最多 10 个模块。不要为满足数量删除真实分支，超过时重新审视业务边界。
- 模块、子模块名字说明“这一段做什么”，同一业务内不重复，不含空格。
- 切分作为范围草案交给用户确认；本轮已确认的不再问。

### 交接写法

| 关系 | 写在哪里 |
| --- | --- |
| 模块交接 | 总览箭头和清单说明交接物；详图用 `==> 模块：名称 / 子模块名` |
| 上下游业务 | 头部放相对链接，图中用 `==> 业务：名称`，不复制对方内容 |
| 共用能力 | 图中用 `==> 能力：名称`，右卡写传入什么，锚点表加能力类型行 |
| 共用数据或接口 | 锚点表加类型行，由脚本汇总到顶层交叉表 |

旧资料默认只当线索，服从项目设置中的使用约定；以当前代码核实，不自动迁移、改写或删除旧资料。脚本只扫描当前目录下 `docs/链路全景/`。

## 2. 文件组织

```text
docs/链路全景/
├── README.md
├── 业务/
│   ├── 账号登录.md
│   └── 订单履约/
│       ├── 总览.md
│       ├── 01-下单.md
│       └── 02-发货.md
└── 能力/
    └── 消息可靠投递.md
```

### 单文件骨架

```markdown
# 账号登录

> 一句话：用户通过一键登录或验证码建立会话。
> 最后核对：实际核对日期
> 需求资料：无；依据当前代码
> 上游业务：无
> 下游业务：需要登录的业务

## 总览

（总览图 + 子模块清单）

## 子模块 1：一键登录

（一个 text 围栏中的双栏图）

<details>
<summary>对应源码入口</summary>

| 节点 | 文件入口 | 精确定位 |
| --- | --- | --- |
| N1.01 | web/pages/login.vue:30 | `beginLogin()` |

</details>

<details>
<summary>规则与字段</summary>

| 节点 | 项 | 内容 |
| --- | --- | --- |
| N1.01 | 重复操作 | 请求未结束时不再发起 |

</details>

## 未核对

（位置、缺什么证据、影响什么判断；没有缺口时写明本次核对边界）
```

头部日期只供人读，脚本不据此判断新鲜度。资料没有就写“无”，不虚构需求链接。

### 目录业务

`业务/<业务名>/总览.md`：一级标题写业务名；包含 `## 总览`、`## 子模块索引`、可选的 `## 规则与字段`、`## 未核对`。

模块文件名为 `01-下单.md`，一级标题必须对应 `# 模块 1：下单`。头部写所属业务链接、上一模块、下一模块、最后核对日期；正文为模块总览、子模块和未核对。

插入模块时同步文件号、清单和链接，变更只涉及本业务；单文件升级为目录时同步其他文档的旧链接。脚本可读已有的业务 `README.md` 和五列模块清单，但新文档使用 `总览.md`，不做无关批量迁移。

所有链接相对当前文档；源码锚点的路径相对运行白泽的当前目录。这两种相对基准不要混用。

## 3. 总览与清单

业务总览要能独立读懂：从触发串到结果，保留条件、失败、重试、取消和关键交接。不能只把模块标题连成一条直线，也不把源码长路径和方法名塞进去。

- 总览一个 `text` 围栏，无外框，最长行不超过 100 格；可以纵向延续。
- 阶段写 `[号] 名称`，与清单一致。箭头上说明输入、触发或交接物。
- 互斥条件从共享判断横向展开，各自向下；真正共享后半段才汇合。
- 独立事件通知和 HTTP 回执不画成必须“等齐”的汇合门。
- 失败、过期、重复消费等走实际出口，不一律连向成功。

```text
检查订单
    |
    +------------------------+
    |                        |
    v                        v
信息齐全                  缺少必填信息
    |                        |
    v                        v
创建订单                  提示补齐后重试
    |
    v
交给支付
```

不要沿同一竖干挂多条 `+--> 条件说明`，那是列表，不是分支图。模块总览交代上游输入、输出和下一模块；独立触发链可空一行分隔，不为右卡对齐而插空行。

### 目录业务的两张清单

模块清单跟在总览图后：

| 模块 | 做什么 | 交给下一步 | 详情 |
| --- | --- | --- | --- |
| [1] 下单 | 校验输入并创建订单 | 待支付订单 | `[查看模块](01-下单.md)` |

`## 子模块索引` 列出所有模块的所有子模块，链接直达标题：

| 模块 | 子模块 | 这一段看什么 |
| --- | --- | --- |
| 01 下单 | `[1 资料检查](01-下单.md#子模块-1资料检查)` | 提交入口和缺项处理 |

上面两个相对链接是格式示意，不是本参考文档中的实际跳转。

单文件业务、模块文件、能力文档使用子模块清单：

| 子模块 | 做什么 | 入口 | 交给下一步 |
| --- | --- | --- | --- |
| [1] 资料检查 | 校验输入 | web/pages/order.vue:30 `submitOrder()` | 有效输入 |

入口必须出现在对应子模块锚点表；完整源码定位留在详情，不复制进上层业务全景。

## 4. 子模块双栏图

每个子模块一个 `text` 围栏，一张整体带外框的双栏图。左栏讲业务，右栏讲实现，按 `[N1.01]` 关联，不拆成两张图。

1. 左栏连续；右卡按传入顺序紧凑排列，卡片间只空一行。两栏不要求逐行对齐，空白只留在较短栏底部。
2. 节点编号 `N<子模块号>.<两位序号>`，文件内唯一，子模块内从 01 连续。仅移动并行支路保留编号；实际增删节点同步图、卡片和锚点表。
3. 一个左栏节点配一张右卡，标题 `[N编号] 层名`。每个节点至少一个源码锚点，可以多行。
4. 卡片按真实职责选层，层名来自项目设置。「能力」固定可用；不要照搬别的项目的分层。
5. 卡片字段：文件、按钮、自动、判断、方法、桥接、插件、前端、接口、依赖、表、缓存、事件、外部、跳转、成功、失败、并发、动作。项目专用字段须在设置的「卡片扩展字段」声明。
6. 右卡长字段按空格、路径分隔符、语句边界续行，后续行缩进两格。方法标识符不拆开；放不下就改用简短动作摘要，完整方法留在锚点表。
7. 跳转用 `==> 子模块 2`、`==> 子模块 2：会话`、`==> 模块：支付 / 扣款`、`==> 业务：订单履约`、`==> 能力：消息可靠投递`。名称续行只能在紧邻下一行同列，不接到另一分支。

层名示例（不是固定白名单）：

| 层名 | 常见职责 |
| --- | --- |
| 页面层、组件层 | 按钮、输入、提示、渲染、跳转 |
| 状态层 | 共享状态、在途请求、响应过期判断 |
| 请求层、接口层 | 客户端请求、服务端路由、响应协议 |
| 服务层、应用层、领域层 | 业务编排、事务、业务规则 |
| 数据层 | 仓储方法、表、缓存、锁 |
| 异步层、调度层 | 消息投递、消费、定时触发 |
| 原生层、外部服务 | 系统桥接、第三方适配器 |

按“这一步做什么”选层，不机械按目录选。表本身不是实现：右卡写读写表的仓储方法，再写表名；外部调用锚到本项目适配器，不伪造外部源码。

## 5. 宽度与生成器

默认整图 99 格：左内容 48，中线绝对列 51，右卡起点 53，右卡宽 44，末边框列 98（从 0 计列）。其他尺寸也不能超过 100 格。

- W/F 全角字符按 1.62 格，其他字符按 1 格，边框与接点误差 ≤0.5 格。这是按 Typora 校准的阅读宽度，不是所有字体的定律；不改成 2 格。
- 只用整数普通空格补齐，不改正文单空格、方法名、接口路径。
- `render_detail()` 生成双栏；`place_at(prefix, value, column)` 在整行绝对列放连接点；`pad_display()` 只补齐单段，不累加多段取整误差。
- 混合中文行上的竖线也用 `place_at()`，不能只对齐纯连接行。

下面是随附的 `examples/render-detail.mjs` 示例。可直接运行 `node "<skill>/examples/render-detail.mjs"`；自定义时复制为同目录下的 `.mjs` 文件，再修改 `left` 和 `cards`。无需安装依赖或设置模块搜索路径。

```javascript
import {place_at, render_detail} from '../scripts/chain_layout.mjs';

const left = [
  '检查资料 [N1.01]',
  '    |',
  '    +-------------------------+',
  place_at('    |', '|', 30),
  place_at('    v', 'v', 30),
  place_at('资料齐全', '缺少资料', 30),
  place_at('    | 保存完成', '| 等待补录', 30),
  place_at('    v', 'v', 30),
  place_at('==> 子模块 2', '( 本次不提交 )', 30),
];
const cards = {
  'N1.01': ['应用层', ['方法：validate()', '动作：校验本次输入']],
};
console.log(render_detail('子模块 1：资料检查', left, cards));
```

生成器不自动证明业务逻辑正确，也不代写锚点表。完整阅读样例见 [账号登录](../examples/账号登录.md)。

## 6. 源码锚点

详图后用 `<details>` 包裹 Markdown 表格，标题固定为 `<summary>对应源码入口</summary>`，HTML 标签与表格之间留空行。解析器兼容 `### 对应源码入口`，新文档用 details。

| 节点 | 文件入口 | 精确定位 |
| --- | --- | --- |
| N1.01 | web/pages/login.vue:30 | 按钮 `.login-button` → `beginLogin()` |
| N1.02 | server/routes/auth.py:20 | `verify_code()`；接口 `POST /api/login/code` |
| N1.03 | server/models/account.py:8 | 表 `accounts` 读写（账号表）；中文注释来源见模型定义 |

规则：

- 固定三列，一个节点可占多行。路径相对当前项目目录，使用 `/`，不加绝对路径或 `..`。
- `路径:行号` 用于跳转，令牌用于识别。整份文件就是锚点时可不写行号，例如模板、配置、提示词文件。
- 反引号里的内容按顺序分类：
  1. 类型词之后的令牌：表、接口、事件、缓存、外部、能力。可接读、写、读写、发布、消费、调用。例如 ``事件 `order.paid` 发布``。
  2. 选择器：`.`、`#` 开头，或 `data-testid=...`。
  3. 符号：标识符与点，可带结尾 `()`，如 `Service.save()`。
  4. 其他内容（路由、表达式）只作说明，不参与检查。
- 清单入口使用同样规则。卡片里的方法应在该节点源码表出现。
- 英文表名保留为身份，中文名称来自数据库注释或 ORM/迁移定义，写在令牌外：``表 `accounts` 读写（账号表）``。来源在括号外，不混进表名；查不到写“中文注释待核对”。
- 当前解析格式不支持包含空格的源码路径、所有语言的符号语法或动态生成路径。遇到这些情况可锚到可表达的注册/配置文件，明确限制，不把文件改名来迁就文档。

## 7. 规则、未核对与顶层索引

### 规则与字段

状态、阈值、公式、字段映射放在独立 `<details>`，标题 `<summary>规则与字段</summary>`，列为“节点、项、内容”。没有就不写。

跨模块规则放在业务 `总览.md` 的 `## 规则与字段`，列为“项、内容、涉及模块”。不要把同一全局规则复制到每个子模块。

### 未核对

每条写位置或节点号、缺什么证据、会影响什么判断。例如“N2.03：任务的部署调度表未取得，不能确认线上触发频率”。未核对不当作已实现；有未提交源码变更时说明以当前工作区为准。

### 能力文档

与单文件业务同结构，头部把上下游换成“调用方”；总览开头写传入什么，结尾写交还什么，不写某条业务专属的消费者和事件值。

### 顶层 README

`docs/链路全景/README.md` 依次放：

- 阅读方式：先业务、再模块、再子模块。
- 全局业务图：业务上下游与共用能力。
- 业务清单：业务、一句话、入口、文档、最后核对。入口用白话，例如登录页「登录」按钮。
- 能力清单：能力、做什么、调用方、文档。
- 交叉表：哪些业务使用了同一个能力、表、接口、事件、缓存或外部服务。

交叉表必须放在以下标记之间，`check --fix` 才会重建；脚本不会替你创建缺失标记：

```markdown
<!-- chain:cross-table:start -->
（脚本生成的表格）
<!-- chain:cross-table:end -->
```

能力引用即列出，其他类型至少被两条业务引用才列出。同业务多个模块合并为一列。交叉表仅依据锚点表，不搜索整个源码来证明“没有其他调用方”。

## 8. 分支核对与验收

### 先追到结果，再画分支

以本次确认范围为界，列出入口和源码实际存在的成功、失败、取消、超时、重试、重复请求分支；不存在的分支不补造。每个分支核对以下事实，把关键结论放进现有「规则与字段」，按节点关联「对应源码入口」，不另存机器流程副本：

| 要核对什么 | 依据与去向 |
| --- | --- |
| 入口与参与者 | 谁从哪个操作或事件进入；独立入口分别接到真实去向，不因属于同一业务就串成前后步骤 |
| 判断条件 | 读取什么状态或字段、条件如何组合；不同结果需要不同后续时不能合并 |
| 状态变化 | 实际写入、界面变化或无操作；有事务、租约或版本约束时核对其生效条件 |
| 交接与消费 | 返回值由谁解释、消息由谁消费、回调如何注册；同步受理与异步完成分别追踪 |
| 终点与回跳 | 成功、拒绝、失败、等待什么事件，或回到哪个模块；重试何时继续、何时结束 |

不能停在“函数返回了”或“已发布事件”：还要读取本项目调用方或消费者如何映射结果。尤其区分“不重复发起”与“继续等待”、“同键重放”与“载荷冲突”、“新建授权”与“复用有效授权”。业务不涉及这些机制时无需套用。只能证明函数存在、不能证明该条件下会进入它时，不画成确定箭头。

纯前端核对本地判断、请求边界、响应分支与界面结果；纯后端或脚本核对请求、任务或命令到返回、状态变化和输出。外部内部实现不在范围时标「外部」，继续核对本项目对其响应的处理。追不下去的按“节点、缺失证据、影响”写入「未核对」，不强行补齐技术层。

### 修复后同步各层

每次修改条件、状态或交接，都按“业务总览 → 模块总览 → 详图 → 规则表和清单”核对涉及位置。检查独立入口是否误合并、失败是否误接成功、等待是否跳过前置条件，以及回跳是否仍指向旧路径。重绘时逐项保留原图已核实的失败、拒绝和回跳出口；需要改变时给出新的源码依据。总览可以省略实现细节，不能改变进入条件或业务结果。顶层 README 或上下游引用涉及同一结论时一并同步；没有涉及的文档不扩大修改。

分工交回时提供文档、关键分支的源码依据、单文件检查结果和未核对项。汇总者负责跨模块交接与总览一致性，文件齐全或各自检查通过不代表整条链路通过。修复后重新核对受影响分支、调用方或消费者，以及相关上层表述；审查结论必须针对最终版本。

### 分开记录验收结果

1. **结构**：运行 `chain.mjs check <本次文档...>`，覆盖修改与同步范围。`check --fix` 只修可唯一定位的行号和交叉表，不改语义或版式；修复后重新检查。锚点修复依赖正则，有歧义留给人工；缺契约时不能宣称接口已核对，非 Git 目录没有新鲜度证据。
2. **源码语义**：按上述事实逐分支核对，交付说明列出关键分支、源码节点及同步位置；具体判断保留在文档中。已知错误或内部矛盾不能以「未核对」掩盖后宣称完成。
3. **显示**：在实际查看器检查最长图和复杂分叉的折行、连线及表格。Typora 原生对 details 内 Markdown 表格的折叠支持有限，需要兼容插件；没有查看器或截图失败，准确列出未验范围。
4. **运行**：只记录实际执行的场景和结果；没有运行环境、部署资料或本次只做静态任务时，明确未执行及限制。不把源码核对、静态检查或合成演练算作业务运行通过。
