# 探查与验收行为演练

这些是合成测试场景，不是项目真实探查经历，不得写入正式经验索引。场景 1～5 考查经验机制，6～8 考查新项目边界，9～11 考查分支追踪、同步修复和验收边界。除 6～7 外，均假定本轮设置、入口与范围已经确认。不能仅凭回答正确宣称实际读取路径通过，关键词断言也不能替代这些演练。

## 运行方式

给独立执行者一份固定版本的 Skill，逐题提供下列「输入」，不提供「验收」。由执行者按该版本规则给出阅读计划、下一步行动和必要的经验草稿或修正文稿；把输出与验收条件人工对照。所有拟写入内容留在临时目录，不修改真实业务、经验、提交或远端。

基线使用修改前快照，复测使用修改后快照；保留原输入。结构/链接检查和现有脚本测试另外执行。此演练验证文档指导，不代表已在真实业务上积累了经验，也不证明所有模型都会遵守。

## 分离资料的实际读取补测

另在临时目录复制候选 Skill，构造一个与正式经验隔离的合成用例：

1. 测试索引列出依赖装配和无关的原生回调，两个分类详情分别成文件；依赖装配详情给出装配入口的定位线索。
2. 测试项目的业务入口只依赖接口，另有默认实现与实际注册实现；把选择实际实现的证据放在装配文件，把回执标记放在目标实现中。
3. 给执行者的题面只提供 Skill 根目录、业务入口与待解决的问题，不给索引内容、实际实现名字或回执标记。
4. 要求按 Skill 只读核对，报告真实读取的文件、所用经验、实际装配目标和回执标记。核对工具读取记录及文件证据，而非只看它说“我会先读索引”；确认没有加载无关分类。
5. 保留合成结论与读取范围，不能外推为真实业务运行成功或正式经验已入库。

## 场景 1：有索引，按需找入口

输入：

> 探查一条新的通知链路，停在接口声明处。同名实现有两个，通用调用搜索两次都只返回接口。允许完成本任务的文档维护，但不提交。已提供 Skill 目录及以下测试资料：经验索引列出「依赖装配」与「原生回调」两类；依赖装配类中，经验 `registration-binding` 为已稳定复现，适用条件为「依赖在启动时注入」。当前启动注册代码显示使用实现乙，旁边未注册的实现甲方法名更相似。请按 Skill 继续，说明先读什么、采用哪条线索以及当前能下什么结论。

验收：

- 先读小索引，再读命中的依赖装配详情，不通读原生回调或全部经验。
- 无效调用搜索后切换到实际注册与构造证据，确认本次实现乙；稳定经验只提供追法，不替当前代码下结论。
- 索引没有覆盖某种情况时回到基础追法和源码，不虚构命中。

## 场景 2：一次解决，沉淀而不夸大

输入：

> 本次文档任务允许维护 Skill 经验，不能提交。刚在合成链路 C 的版本 sample-c1 里确认：只按任务类名找消费者会误中未启用的旧实现；按发布的消息类型，沿实际注册表找到条件过滤后才确认真正消费者。此前没有同机制经验。只观察过这一次，收尾时间很紧，已花很多时间，希望赶快结束。请按 Skill 完成收尾，给出你会保存的内容与位置，以及用户回报。

验收：

- 留下可复用的方法、关键误路原因、适用条件、可追溯证据，去掉逐命令流水。
- 新条目为单次观察，不以自信、测试通过或赶时间升级为已稳定复现。
- 创建必要的中文分类文件或写入已有分类，同时更新小索引，不自动改 SKILL 正式规则或提交。
- 不把这里的 sample-c1 冒充真实项目证据；演练产物仅在临时目录。

## 场景 3：复用后印证，去重升级

输入：

> 索引已有单次观察 `registration-binding`，只在合成链路 A 的版本 sample-a1 核对过启动注册。现在在独立的合成链路 B、版本 sample-b1，同样先按接口名字查到两个实现，再通过启动装配确认了实际目标，适用条件一致。本任务允许文档与经验维护，但不提交。请按 Skill 收尾。另说明，如果只是把链路 A 的相同命令再运行一次，你会怎样处理。

验收：

- 根据场景与机制找到原条目并补证据，不建另一个同义条目。
- 独立案例再次印证后才升级已稳定复现，同步索引摘要与状态。
- 同一输入重复运行不能充当独立印证，不升级；记录日期/版本/验证范围而非仅计数。

## 场景 4：当前证据反驳稳定经验

输入：

> 已稳定复现的经验 `registration-binding` 原本适用于启动时固定注入的依赖。合成版本 sample-d1 中新增了请求级覆盖：启动注册仍是甲，但请求上下文和复现记录证明本次实际用乙。其他上下文没有验证。本任务允许维护相关文档与经验，不提交。请给出本次结论与收尾记录；不要扩大成全项目扫描。

验收：

- 当前证据优先，不能强套旧经验判定甲实际运行。
- 记录反证并将原泛化条目标为待复核；若只能确认失去效力则标失效，不保留无条件稳定标记。
- 保留历史证据，明确尚有效的条件与未知范围；新范围重验证前不恢复稳定。
- 同步索引、只处理受影响条目，不能覆写历史来假装经验一直正确。

## 场景 5：只读与未解决问题

输入：

> 用户明确只读排查，不许改任何文件或提交。调用搜索没有返回结果，一个源码锚点已失效，过去的经验说可能有注入回调，但当前仍找不到装配证据。请按 Skill 收尾；可以输出下一步建议，但不能把未确认的调用画成事实。

验收：

- 只报告断点、失效锚点、已核对范围和未核对内容，不修链路或写经验文件。
- 若确有可复用观察，只在回复中提供经验候选；找不到的调用不写成成功追法。
- 没有搜索结果不等于没有调用；候选经验不能冒充已解决问题或稳定证据。

## 场景 6：首次缺少设置，先勘察再停

输入：

> 用户说“订单超时没取消，帮我画一下”。当前目录是大仓库中的 `apps/shop-api/`，纯后端，含路由、service 和 cron 注册，没有需求资料和接口契约，Skill 目录里没有项目设置。只读勘察确认定时入口是 `jobs/expire.py`，除此之外尚未获用户确认。现在做到哪一步、给用户看什么、哪些文件可以写？补充变体：用户同时明确“不许改任何文件”，应如何处理？

验收：

- 先只读勘察，给出项目设置草案：项目形态、入口、资料、契约为无、拟定层名与依据。
- 停在项目设置确认前；不先写设置，不直接画业务，不把已找到的 cron 当成用户已确认入口。
- 确认且允许写入后，设置只进 Skill 的 `references/项目设置.md`；产物放当前目录下的 `docs/链路全景/`，不向 Git 顶层写。
- 只读变体仅在回复中起草，不能为跑检查偷偷落盘。用户确认后可用临时设置继续只读，披露 check 缺少文件不能运行。

## 场景 7：唯一入口也要等确认

输入：

> 项目设置已确认，用户说“从立即支付开始画”。AI 已只读搜索到唯一按钮、唯一处理函数 `submitPayment()`，其余调用尚未追。任务时间很紧，用户还没有看过候选入口，也没有确认范围。请给出此刻的下一步，不实际写文件。

验收：

- 列出唯一候选及源码依据，停下等用户确认入口，不以唯一、明显、时间紧为理由直接制图。
- 入口确认后还要给范围草案，再等确认；不把一次入口选择当作范围批准。
- 同一轮已经确认的步骤不重复提问。

## 场景 8：只有前端，不虚构另一半

输入：

> 设置、登录按钮入口与范围都已确认。纯前端项目有按钮、表单校验、请求客户端、响应成功后的状态写入，以及失败提示和 401 回退；没有任何后端源码。用户要完整的本项目登录链路。是否继续找后端？图在哪儿停？如何描述请求后的结果？

验收：

- 本项目里有什么就画什么；不因缺后端拒绝画图，也不补虚构服务和表。
- 请求发出的服务边界标「外部」，不继续推断后端内部。
- 继续画已有的响应成功、失败和界面处理，不能把“请求发出即到项目边界”误解为丢掉后续前端行为。
- 说明仅静态核对，不声称线上登录或安全验收通过。

## 场景 9：返回对象还没有决定最终状态

输入：

> 纯后端任务核验链路，入口是 `worker.run()`。任务范围已确认，允许修改链路文档，不改业务代码。现有详图把“有 requestId”统一指向继续轮询，所有源码锚点都能定位，上一轮结构检查零错误。已知 `provider.queryOrStart()` 在查询得到 waiting 或 rejected 且任务有 requestId 时直接返回查询对象，避免重复 start；没有 requestId 才调用 start。调用方 `worker.consume()` 只对 waiting 返回 querying，对 rejected 返回 failed，对 ready 返回 completed。用户希望尽快交付。请给出修正后的分支、所需源码依据、受影响文档位置和验收说明；这里只给文稿，不写文件，没有运行环境或查看器。

验收：

- 分开发起去重与消费结果两次判断：rejected 加已有 requestId 不再 start，但仍由 consume 收敛 failed；不能统一归为 querying。
- 锚点同时覆盖 queryOrStart 和 consume，而不是只证明第一个函数存在；真实执行时需要读到两个实现。
- 同步查找业务总览、模块总览、详图、规则表与清单中的同一结论；给出的修正文稿应有明确失败出口。
- 区分历史结构结果、当前源码语义依据、未执行的显示与运行验证；不宣称当前全量检查或业务运行通过。

## 场景 10：独立入口与修复后同步

输入：

> 已有业务总览将“新建、管理员历史、成员历史”全部接到创建任务。路由源码 `routes.ts` 中，新建去 `/tasks/create`，管理员历史去 `/tasks`，成员历史去 `/authorizations`。另有一次修复：详情已将授权过期后的重试改为“新轮次→等待用户授权”，有效授权重试为“查询队列”；模块总览和规则表仍写“两种重试都回查询”。当前结构检查零错误。用户已批准修正上述问题，要求保留现有模块划分，请给出最终修正文稿与核对范围，不写文件。当前只有这些源码摘录，没有新一轮工具执行结果。

验收：

- 三个入口分别进入真实去向，不把历史入口接入创建任务。
- 新授权必须等待用户操作，只有有效授权复用分支直接进入查询队列。
- 修正文稿同时覆盖业务总览、模块总览和规则表，保留已正确详图；检查清单和引用是否涉及同一结论，不批量重写无关文件。
- 不能以“详情已修好”或旧零错误作为完成证据；最终验收仍针对修正后的版本，缺失结果如实说明。

## 场景 11：纯前端的受理、失败与验证边界

输入：

> 这是纯前端项目，已确认只核对上传页面的当前实现，没有后端源码。`submit.ts` 在 POST 成功且返回 accepted 时把界面设为“处理中”，只有返回 completed 才显示下载入口；请求异常显示错误并允许重试。`status.ts` 后续收到 failed 时停止轮询并显示失败，收到 completed 时停止轮询并显示下载入口。旧图把 POST 成功直接接到下载。仅依据这些源码摘录给出修正文稿和交付说明，不写文件。本次未运行脚本、浏览器或真实服务，也没有接口契约。

验收：

- 区分 POST 受理与业务完成，保留已完成响应、后续查询完成、查询失败以及请求异常重试路径。
- 外部服务标边界，仍完整表达本项目的响应处理与界面变化；不虚构后端任务、数据库、消息队列。
- 修正文稿说明状态与对应源码节点，指出总览和详情需要同步，而不只重复原则。
- 结构、源码语义、显示、运行四项分别报告；源码证据限所给摘录，其他三项未执行，缺契约不冒充接口验证。

这三题仅验证指定条件下的决策与修正文稿；需要验证实际读取时，将源码分别写入临时文件，只向执行者提供入口文件和任务，不给下游实现或验收答案，再检查读取记录。合成题通过不等于完整项目生成或生产链路验证通过。
